## 为什么作业显示失败，但 CSV 仍可复算

4K 与 16K 客户端均以 0 退出，四轮成功请求与输入/输出 token 数符合固定工作负载，所有汇总列与第 2–4 轮平均一致。控制器在负载结束后找不到 `FL KV-decode fusion entered` 日志而报错，故两个守护终态仍为 `FAILED_OR_STOPPED`。已确认 cleanup=true；不把这两个终态改写成通过。

后续日志审查指出，插件 logger 在该环境有效级别为 WARNING，而原见证使用 INFO；因此“日志缺失”不能证明零命中。反之，说明日志级别问题也不能证明正式长测实际命中。

独立、非计分诊断覆盖：

- v2：64/64 个 4K 请求成功，观察到 `4k-s16` 在 capacity32/64 的真实执行。
- v3：17/17 个 16K 请求成功，观察到 `16k-s32` capacity1 的尾段执行；17 请求落入原 capture24，不能用于证明 capacity32。
- v4：25/25 个 16K 请求成功，EngineCore 121318 记录 capacity32 下 `fused_active_25` 和 capacity1 尾段。

这些是独立诊断的执行路径证据。事件为受限/首次观察，缺少完整分母；不据此生成命中比例，也不把其诊断耗时写入正式成绩。

## 下一次天数测试的最小必要集合

1. 先用短诊断记录每个 Graph bucket 的请求期执行与回退原因，包含总调度步数、有效 token、上下文范围；计数区分 capture 与 replay，最后可靠落盘。该诊断不计分。
2. 采用正常安装包、原版和候选相同的日志配置，让“首次命中”证据不会被 logger 级别吞掉。保持官方 serve 与 Benchmark 不变；正式运行只做低频身份/首次命中记录，不开启逐步重日志。
3. 同一设备、同一软件栈先跑原版与候选对照，再决定是否反序复验。短测只用于淘汰明显问题，不代替完整四轮。16K 很稳定但低于外部参考，先核对原版水平及调度覆盖；4K 则需同时检查已有较大波动。
4. 在命中、精度和性能证据补齐前保留 formal4 为候选，不让它覆盖历史原版、旧诊断结果或最终保底状态。
